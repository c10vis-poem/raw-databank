## Part 1 — Definitive spec: `MAP.md` vs `manifest.jsonl`

These are two DIFFERENT artifacts with two DIFFERENT audiences and two DIFFERENT read triggers. Any agent operating in the vault MUST know exactly when to reach for which.

### 1.1 `MAP.md` — the human/agent navigation index

- **Audience:** Human operators + agents doing exploratory / orientation reads
- **Format:** Markdown with bidirectional `[[wikilinks]]` — same format as the wiki itself
- **Content:** Top-level headings for every organizational cut (`## Domains`, `## Vendors`, `## Agents`, `## Projects`, `## Runbooks`), each with links to the leaf notes
- **Size:** Bounded — grows linearly with tree size, NOT with file count. Should stay browsable in one screen with Ctrl-F.
- **Update trigger:** Any structural change (new subfolder, new project, new agent, new vendor). NOT on every leaf-file change.
- **Read trigger:** **First read on session start.** Human or agent asks "what's here?" — MAP.md answers.

### 1.2 `manifest.jsonl` — the machine RAG index

- **Audience:** Retrieval engines, RAG queries, agent search, hash verification
- **Format:** JSON Lines — one JSON object per file, streamable
- **Content:** Per-file record with `id`, `path`, `tier`, `category` (one of 5 doc types), `sha256`, `tokens`, `semantic_summary`, `entities_extracted`, `retrieval_tokens`, `provenance_source`, `last_synced`
- **Size:** Grows linearly with FILE COUNT. Can be tens of thousands of lines.
- **Update trigger:** Every file add/modify/delete anywhere in the vault. Automated hook.
- **Read trigger:** **Not read whole; queried.** When an agent needs "find all Reference-type files tagged `qairt`", it streams the JSONL and filters. Never loaded fully into context.

### 1.3 The agent's first-move directive (canonical, non-negotiable)

Every agent operating in the vault MUST follow this sequence on first read:

```
1. Read root MAP.md (bounded, one screen)  →  Orient: "what's here"
2. Optionally read the MAP.md of the specific tier you'll work in  →  Focus
3. Query the tier's manifest.jsonl (never load whole; filter by category/tokens/entity)
   →  Locate specific files
4. Load only the specific files the manifest points to
   →  Read
```

**Anti-pattern (banned):**
- Loading `manifest.jsonl` fully into context — it's a stream, not a document
- Skipping `MAP.md` and going straight to `find . -name '*.md'` — wastes tokens on discovery
- Editing `MAP.md` on every leaf-file change — MAP.md is structure, not file-list
- Editing `manifest.jsonl` by hand — it's regenerated by `generate_jsonl_markers.py`

### 1.4 Fractal: every tier has both

- **Root:** `/MAP.md` + `/manifest.jsonl`
- **Tier 1:** `/01_raw_sources/MAP.md` (tier-local, links to raw source subfolders) + `/01_raw_sources/manifest.jsonl` (only Tier 1 files)
- **Tier 2 (master wiki, richer per Part 3 below):** `/02_wiki_md/MAP.md` + `/02_wiki_md/manifest.jsonl`
- Same for Tiers 3, 4, 5

Any sub-tier folder can OPTIONALLY have its own MAP.md if it's deep enough to warrant one (e.g., `02_wiki_md/domains/models/MAP.md` if the models directory has 20+ notes).

**Rule:** MAP.md exists where "what's here" is not obvious from a directory listing. manifest.jsonl exists at every tier root, mandatory, no exceptions.

## Part 2 — Terminology Glossary (canonical definitions)

Every time a term is used differently, it's a bug. These are the ONE meaning each term has going forward. Any doc that uses a different meaning gets corrected.

| Term | Definition | Example (in this stack) | NOT this |
|---|---|---|---|
| **SDK** | Software Development Kit — a set of headers, libraries, docs, and compiler-time tools a developer uses to BUILD an app that targets a specific platform | Qualcomm QAIRT SDK (build against Hexagon NPU), Android NDK (build native code), Video Game SDK (build with performance-hint APIs) | Not a runtime, not a server. You don't "run the SDK" — you use it to compile something that then runs. |
| **Runtime** | The library or environment that executes compiled code AT RUNTIME on a device. Ships as `.so` / `.dll` / `.dylib` / kernel modules. | QAIRT runtime (`libQnnHtp.so`), llama.cpp runtime, ONNX Runtime, Android RT | Not the SDK you built with, not the model file, not the agent harness. It's the executor that loads the model + services calls. |
| **Engine** | A high-level executor that wraps a runtime + a model + a scheduler into a single serving surface | GenieX (wraps llama.cpp + GGML Hexagon backend), whisper.cpp engine, Piper TTS engine | Not the runtime itself; the engine SITS on the runtime. Not the SDK; the engine USES the runtime the SDK produced. |
| **MCP server** | A process implementing the Model Context Protocol — exposes tools/resources over stdio or HTTP for MCP clients (Claude Code, ECC, etc) to call | `@modelcontextprotocol/server-filesystem` (Node.js, gives agents filesystem access), OmniRoute MCP server, SQLite MCP server, Postgres MCP server (OB1 grounding) | Not an agent, not a harness, not a runtime. It's a protocol adapter. Multiple MCPs coexist naturally — each does one narrow job. |
| **Harness** | The outer control-loop program that manages an AI agent's execution: what tools it has, what memory it sees, how it recovers from failure, how it chains steps | ECC (governs Claude Code sessions), Prime Agent (governs on-device open-weight models via RLM), GSD v2 (build-phase harness), DeepSeek harness (coming) | Not the model, not the runtime. The harness INVOKES the runtime/engine. |
| **Agent** | A specific configured persona/role running under a harness, with a defined purpose, memory scope, and tool allowance | Œræcle (help-desk oracle role, `oeracle_helpdesk.yaml`), File Administrator (housekeeping role, `file_administrator.yaml`), Red Auditor (incognito verifier), Cross-Auditor (public enterprise auditor), Early-Trend Scraper | Not the harness (many agents can run under one harness). Not the model (one agent may switch models). |
| **Model** | The trained neural network weights — a static file (GGUF, ONNX, safetensors) | Qwen 3.5 0.8B, Qwen 3.5 9B, Gemma 4 12B, DeepSeek, Phi-4-Mini | Not the engine that runs it, not the harness that invokes the engine. |
| **Weights** | Synonym for model file; used when emphasizing the artifact vs the concept | `Qwen3.5-2B-Q4_0.gguf` (1.21 GB, already on disk) | — |
| **Protocol** | A specification for how components communicate. Not code — a document/schema. | Æsop-Xi (ethical arbitration protocol), MCP (tool-use protocol), Universal JSONL Marker Schema, W5+H matrix, ADB loopback protocol | Not the implementation that follows it. |
| **Daemon** | A long-running background process, typically registered as a system service | Æsc APK daemon, Æyre APK daemon, NPU manager daemon, Red Auditor daemon (in `.red/`) | Not a one-shot script; must survive across the parent process. |
| **CLI** | Command-line interface — the terminal-visible entry point | `openwiki`, `claude`, `gh`, `graphify`, `notebooklm`, `geniex infer`, `genie-t2t-run` | Not the underlying runtime; the CLI is a user-facing wrapper. |

### 2.1 Concrete example applying the glossary

- Qualcomm ships the **QAIRT SDK** (compile-time tools + headers for Hexagon NPU)
- You use the SDK to produce a pre-compiled Qwen 3.5 0.8B **model** bundle (a Genie bundle from QAI Hub)
- The bundle runs on the **QAIRT runtime** (`libQnnHtp.so`) via HTP0 (Hexagon NPU v79)
- `genie-t2t-run` is the **CLI** that invokes the runtime
- **GenieX** is a higher-level **engine** that wraps the runtime + scheduler + `llama_cpp` for GGUF models
- **Prime Agent** is the **harness** that treats GenieX as one tool among many in its RLM loop
- **Œræcle** is an **agent** — a specific persona (help-desk oracle) running under the Prime Agent harness with the 9B model + mem0 + OB1 tools

Every doc, from now on, uses these terms with exactly these meanings.

### 3.1 What "extraction" means (glossary addition)

**Extraction = the act of pulling structured content out of unstructured input.** Examples:
- **Data extraction** — OmniRoute intercepts every prompt/response passing through `localhost:20128/v1`, classifies content, and extracts memory-worthy facts into Reasoning Bank + mem0 + OB1 (this is why OmniRoute IS a memory extraction layer per operator directive)
- **Skill extraction** — reading a doc and pulling out reasoning heuristics into `04_skills_runtime/prompt_skills/`
- **Tool extraction** — reading a doc and pulling out executable snippets into `04_skills_runtime/extracted_tools/`
- **Voice extraction** — Moonshine STT extracts text from audio
- **Screen extraction** — Æyre's Video Game SDK vision layer extracts frame arrays from screen capture

Voice is a subclass of extraction (audio → text), so `protocols/extraction/voice-extraction.md` makes sense.

## Part 6 — KAG Recurse + RAG Pipeline + KV cache vs SQL

Three items that were missing definitional clarity.

### 6.1 KV cache vs SQL

| Aspect | **KV cache** | **SQL (SQLite / Postgres)** |
|---|---|---|
| **Purpose** | Store attention-key/value tensors from a running LLM inference so subsequent tokens don't re-compute prior context | Store structured records (user facts, session state, agent trajectories, RLVR verdicts) queryable via SQL |
| **Scope** | Ephemeral, per-inference — dies when the model unloads | Persistent, cross-session |
| **Location** | GPU/NPU VRAM primarily; can spill to CPU RAM | Disk (SQLite) or network server (Postgres) |
| **Access pattern** | Sequential-write, sequential-read (during attention) | Random-access via indexed queries |
| **Serialization** | Binary tensors (fp16/int8) | Rows in tables (or JSON columns) |
| **In this stack** | Managed by GenieX / QAIRT runtime; not user-facing | SQLite in `~/.omniroute/*.db` for OmniRoute; Postgres on Node Beta for OB1 |
| **Concurrency** | Single writer (the running model) | File-locked (SQLite) or MVCC (Postgres) |
| **Together AI OSCAR relevance** | OSCAR spec is a 2-bit attention-aware KV cache compression scheme — reduces VRAM cost of long context | (not applicable) |

**They are NOT competitors.** KV cache is a runtime optimization inside the model; SQL is application-level durable storage. They don't touch each other.

### 6.2 Recursive KAG (Knowledge-Augmented Generation) loop

```
[Agent receives query]
       │
       ▼
[Query the JSONL manifest for candidate files]  ←── Round 1
       │
       ▼
[Load candidates into context; agent reasons]
       │
       ├─── Answer sufficient? ──── YES → return answer
       │
       ▼ NO — agent identifies a KNOWLEDGE GAP
       │
[Formulate a new query against manifest]  ←── Round 2
       │
       ▼
[Load new candidates; agent reasons with combined context]
       │
       ├─── loop until sufficient OR max-rounds reached
       │
       ▼
[Return answer + provenance chain (which files at which round)]
```

**Key difference from plain RAG:** RAG does one retrieval → answer. KAG does N retrievals, each shaped by what the previous round revealed. The RECURSION is agent-driven — the agent decides when to loop.

### 6.3 RAG pipeline in this stack

```
[Ingestion side]
Raw docs → convert_raw_to_markdown.py → 01_raw_sources/*.md
       → generate_jsonl_markers.py → per-tier manifest.jsonl entries with retrieval_tokens + semantic_summary
       → chunking → 03_recall_cache/jsonl/*.jsonl (pre-tokenized 256-token chunks)
       → embedding → 03_recall_cache/vectors/*.faiss (dense vectors)

[Query side]
Agent query
    → Read root MAP.md (orientation, one-screen)
    → Query root manifest.jsonl → identify candidate tiers
    → Query tier manifest.jsonl → filter by category / retrieval_tokens
    → For each candidate: check 03_recall_cache/vectors/ for semantic-similarity ranking
    → Load top-N chunks from 03_recall_cache/jsonl/ into context
    → If insufficient: enter KAG recursion (§6.2)
    → Answer + provenance chain
```

**Both flows share `03_recall_cache/` as the fast-lookup layer.** SQL (SQLite) is used ONLY for KV pairs (entity lookups, session state) — not for the RAG chunk store.

## Part 8 — Modular hot-swap for harnesses

Design constraint: swapping ECC ↔ Prime Agent ↔ DeepSeek without cascading changes.

**The abstraction that makes this work:** every harness talks to the world through 4 well-defined interfaces:
1. **Model interface** — an OpenAI-compatible HTTP endpoint (via OmniRoute)
2. **Memory interface** — MCP servers (mem0 MCP, OB1 MCP, Reasoning Bank MCP, filesystem MCP)
3. **Tool interface** — MCP servers (filesystem, SQLite, terminal shell, screen vision)
4. **Output interface** — writes to `05_episodic_logs/trajectories/YYYYMMDD_session.jsonl`

Any harness that speaks these 4 interfaces is a drop-in replacement. The harness catalog in `harnesses/` documents each harness's coverage of the 4 interfaces + any harness-specific quirks. Hot-swap procedure:

1. Stop the outgoing harness (leaves state in mem0 + Reasoning Bank + trajectories/)
2. Start the incoming harness — it reads mem0 + Reasoning Bank on init to hydrate context
3. Trajectory tail from the outgoing harness is available to the incoming one via the shared `05_episodic_logs/` write surface
4. No shared in-process state; no RPC between harnesses

**Consequence:** you can swap Prime Agent → DeepSeek harness mid-project without losing conversation state — because the state lives in mem0/OB1/Reasoning Bank, not in the harness.

Spec doc: `architectures/modular-hot-swap/`.
